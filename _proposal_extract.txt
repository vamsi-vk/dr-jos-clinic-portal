1. Executive Summary
Dr. Jo’s Skin Revive Clinic currently uses MioSalon (Standard Plan) as its primary clinic management platform for appointments, billing, patient records, and day-to-day operations. The clinic’s team is well-versed in MioSalon and relies on it comfortably. There is no intent to migrate away from this system.
However, MioSalon’s Standard Plan does not support custom patient intake forms, additional clinical field groups, extended patient profile views, or custom report generation — capabilities that are essential for a specialist dermatology and aesthetic practice.
3F Advanced Techno Labs Pvt. Ltd. proposes a lightweight, non-invasive extension layer that sits on top of MioSalon without replacing it. The solution consists of three tightly integrated components:

①  A Chrome Extension that injects custom UI panels directly into the MioSalon web interface
②  A Next.js Web Application as the backend portal for managing forms, fields, field groups, and reports
③  A PostgreSQL Database storing all extended patient data, form submissions, and custom field definitions

The clinic continues using MioSalon exactly as before. The extension augments the MioSalon interface with additional panels for intake forms, custom fields, and reports — all appearing natively within the same browser window.
This engagement is scoped for a single full-stack developer over 6 weeks (approximately 1.5 months).

2. Current State & Problem Statement
2.1 What MioSalon Standard Plan Provides
MioSalon Standard Plan delivers a solid core of clinic operations that the Dr. Jo’s team uses daily:
Appointment booking and calendar management
Patient records with standard demographic fields
Billing, invoicing, and payment tracking
Staff and role management
Basic reporting on appointments and revenue

2.2 Gaps for a Specialist Dermatology Practice
A specialist dermatology and aesthetic clinic requires additional clinical data capture that MioSalon Standard Plan does not support:

Custom Intake Forms
No ability to create procedure-specific onboarding forms for new patients (skin type, allergy history, treatment consent pre-screening, etc.)
Custom Field Groups
Patient profiles cannot be extended with grouped clinical fields (e.g. Skin Assessment, Laser History, Medical Clearance)
Custom Field Types
No support for dropdowns, multi-select, date pickers, or signature fields beyond standard MioSalon fields
Extended Patient Views
No way to surface custom clinical data within the patient profile view inside MioSalon
Custom Reports
Standard reports cover appointments and revenue only; no custom clinical or operational reports

The objective of this engagement is to close these gaps without disrupting the clinic’s existing MioSalon workflows.

3. Proposed Solution
The proposed solution is a three-component extension platform that augments MioSalon’s Standard Plan interface without any integration into MioSalon’s internals or API. All components work together transparently.

3.1 Component 1 — Chrome Extension (UI Injection Layer)
The Chrome Extension is the user-facing component. It is installed once on clinic computers and runs automatically when staff open MioSalon in Chrome.

Detects the active MioSalon page (patient profile, appointment, new patient form) using DOM observation
Injects a custom side panel or embedded section into the MioSalon UI showing additional clinical fields relevant to the current patient
Renders the client onboarding intake form when a new patient record is opened
Displays custom field groups (e.g. Skin Assessment, Laser History) as collapsible sections within the patient profile page
Loads and saves all custom field data via the Next.js backend API — MioSalon’s own data is never modified
Supports digital signature capture inline within injected forms (canvas-based)
Extension is silent and non-intrusive — MioSalon’s own UI remains fully functional

3.2 Component 2 — Next.js Web Application (Admin Portal + API)
The Next.js application serves two purposes: a REST API consumed by the Chrome Extension, and an admin portal for clinic managers to configure forms and view reports.

Form Builder: create and manage intake form templates with drag-and-drop field arrangement
Field Group Manager: define custom field groups and the fields within them (text, dropdown, multi-select, date, boolean, signature, textarea)
Patient Data Portal: view extended patient data by MioSalon patient ID, with all custom field groups displayed
Report Builder: generate custom clinical reports by date range, field value, or patient segment
Export: CSV and PDF export for custom reports
REST API: all Chrome Extension read/write operations go through authenticated API endpoints
Deployed on Vercel (zero-maintenance hosting) or any cloud VM

3.3 Component 3 — PostgreSQL Database (Extended Data Store)
PostgreSQL stores all data created by the extension layer. MioSalon’s own database is not touched.

Patient extended profiles keyed on MioSalon patient ID
Intake form templates and submitted form responses
Custom field group definitions and field value records per patient
Digital signature blobs linked to patient + form submission records
Audit log of all field edits with timestamp and staff user ID

4. How It Works — User Flow
From the clinic staff perspective, the workflow is simple and requires no change to how MioSalon is used:

Step 1 — Open MioSalon
Staff open MioSalon in Chrome as normal. The extension loads silently in the background.
Step 2 — Open a Patient Profile
When a patient profile page loads, the extension detects the patient ID from the URL/DOM and fetches their extended data from the Next.js API.
Step 3 — Custom Panel Appears
A custom panel is injected alongside the standard MioSalon patient view, showing all configured field groups (Skin Assessment, Laser History, Medical Clearance, etc.).
Step 4 — New Patient Intake
For new patients, the extension injects the intake form as an additional step within the MioSalon new patient flow. Staff fill the form; data saves to the PostgreSQL backend.
Step 5 — Save Extended Data
Staff fill or update custom fields. On save, the extension calls the Next.js API to persist the data. No MioSalon data is changed.
Step 6 — Reports
Clinic managers open the Next.js admin portal (separate URL) to run custom reports, export data, or update form/field configurations.

6. Data Architecture
6.1 Core Data Model
All records are keyed on the MioSalon patient ID extracted from the MioSalon page URL/DOM — no API access to MioSalon is required.

patients
Extended patient profile (miosalon_patient_id, clinic_id, created_at, metadata)
form_templates
Intake form definitions (name, fields[], version, active flag)
form_submissions
Submitted intake forms per patient (patient_id, template_id, data JSONB, submitted_at, staff_id)
field_groups
Custom field group definitions (name, description, display_order, active)
field_definitions
Field specs within a group (name, type, options[], required, display_order)
field_values
Actual field values per patient per field (patient_id, field_id, value, updated_at, updated_by)
signatures
Signature blobs linked to form submission (submission_id, blob_url, signed_at)
audit_log
Immutable log of all create/update events (table, record_id, staff_id, old_value, new_value, ts)

6.2 Key Design Decisions
MioSalon patient ID is used as the foreign key throughout — extracted directly from the browser DOM, no MioSalon API needed
Field values stored as typed JSONB columns for flexibility as field configurations evolve
Form template versions are immutable once submissions exist — new versions create a new template record
Audit log is append-only; no application role can update or delete audit records

7. Chrome Extension — Technical Detail
7.1 Manifest V3 Structure
manifest.json
Permissions: activeTab, storage, identity. Host permissions scoped to *.miosalon.com only
background.js
Service worker: manages auth token refresh and cross-tab state
content_script.js
Injected into MioSalon pages: DOM observation, patient ID extraction, panel mounting
popup.html / js
Extension toolbar popup: staff login, connection status, quick-access links
injected_ui/
React components compiled and bundled (Webpack/Vite) for injection into MioSalon DOM

7.2 DOM Injection Strategy
Content script uses MutationObserver to detect MioSalon page navigation (SPA route changes)
Patient ID extracted from URL path pattern (e.g. /patients/12345) and confirmed against DOM element
Extension appends a shadow DOM root to a stable MioSalon container element to prevent style conflicts
Injected panels use scoped CSS (Tailwind prefix or CSS modules) — no bleed into MioSalon styles
Graceful degradation: if a MioSalon DOM element changes, the extension logs an error and hides the panel without breaking MioSalon

7.3 API Communication
All extension API calls go to the hosted Next.js backend over HTTPS
Extension authenticates using a short-lived JWT issued at staff login (popup login flow)
API responses are cached in extension storage for 60 seconds to reduce latency on page navigation
Optimistic UI updates: field saves show immediately in the panel while the API call completes in the background

8. Custom Forms & Field Groups
8.1 Client Onboarding Intake Form
A configurable intake form displayed when a new patient record is first opened in MioSalon. Default sections include:
Personal background: preferred name, date of birth, occupation, referral source
Skin profile: skin type, primary concerns, known sensitivities, previous treatments
Medical background: chronic conditions, current medications, allergies, contraindications
Consent pre-screening: yes/no checkboxes for procedure eligibility questions
Digital signature block: patient signature captured on touch screen or via mouse
All sections and fields are configurable by the clinic admin in the Next.js portal. New fields can be added without any code change.

8.2 Custom Field Groups (Patient Profile Extension)
Field groups appear as collapsible sections inside the injected panel on the patient profile page. Example groups:

Skin Assessment
Fitzpatrick skin type, TEWL rating, sebum level, pigmentation notes, last assessment date
Laser History
Treatment dates, device used, energy settings, session count, response notes
Medical Clearance
Cleared by (doctor name), clearance date, conditions noted, expiry date
Before/After Notes
Structured before and after observation text blocks per treatment episode
Lifestyle Factors
Sun exposure habits, skincare routine, diet notes, stress indicators
New field groups can be created in the admin portal at any time and will appear in the Chrome Extension immediately.

8.3 Supported Field Types
Short text, long text (textarea)
Number, decimal
Single-select dropdown, multi-select checklist
Date, date range
Boolean (yes/no toggle)
Digital signature (canvas capture)
Section header (non-input, for visual grouping within a form)

9. Custom Reports
The Next.js admin portal includes a report builder that operates entirely on data stored in the PostgreSQL database. Reports are not dependent on MioSalon’s own reporting.

New Patient Intake Report
All intake form submissions by date range; exportable as CSV or PDF
Custom Field Value Report
Filter patients by any custom field value (e.g. all patients with Fitzpatrick Type IV skin)
Incomplete Intake Report
Patients who have attended but have no submitted intake form on record
Consent Status Report
Patients with / without completed digital signature on intake form
Field Audit Report
All changes to a specific patient’s custom fields with timestamp and staff user
All reports support date range filtering, column selection, CSV export, and PDF export.

12. Risks & Mitigations
MioSalon DOM changes
MioSalon may update its UI and change DOM selectors. Mitigated by using multiple selector fallbacks, MutationObserver re-detection, and a DOM health check on extension load that alerts admin if selectors break.
Chrome Extension policy
Chrome Web Store policies or enterprise Chrome policies may restrict extension installation. Mitigated by offering the extension as a developer-mode sideload for internal clinic use (no Store listing required).
Data sync correctness
Extension reads patient ID from DOM; if MioSalon changes URL pattern, linking breaks. Mitigated by using two independent extraction methods (URL pattern + DOM element) with fallback.
Scope creep
Additional field types or report customisations requested during build. Managed via a defined backlog; items outside scope are queued for Phase 2.
